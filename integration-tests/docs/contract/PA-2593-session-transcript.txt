## What `.spectral.yaml` does

Spectral is a linter for the spec file. It reads only `pipeshub-openapi.yaml` and never looks at the code. It checks three types of things:

- **Structure.** The file must be a valid OpenAPI 3 document. Each operation must have an `operationId`, a tag, a security scheme, and a success response. Each path parameter must be declared.
- **Documentation text.** Operations, request bodies, and tags should have descriptions. Examples should match their schemas.
- **Style.** Path segments should be camelCase and should have no trailing slash.

Spectral cannot tell you if the spec is true. For example, a spec can say a field is a string when the API returns a number, and Spectral will still pass. It only checks that the documentation is complete and well formed.

## What `oasdiff` does

`oasdiff` compares two versions of the spec: the spec on `main` and the spec in the PR. It fails the PR if the change breaks clients. Some examples of breaking changes:

- You remove an endpoint.
- You remove a response field.
- You add a required request parameter.
- You change the type of a field.

This protects SDK users from changes to the spec. But it compares the spec with the spec only. It does not check the code. If the code changes and the spec stays the same, `oasdiff` reports nothing.

## New plan: use real API behavior as the source of truth

We cannot trust Zod or any other file that people maintain by hand. So the only reliable source is what the API really receives and returns. Without integration tests, we get this data from normal traffic.

### 1. A spec-check middleware in report-only mode

Add an Express middleware to the Node API behind an env flag. For each request, it does these steps:

1. It finds the `operationId` that matches the request.
2. It validates the request against the spec with Ajv, for example with `express-openapi-validator` in log-only mode.
3. It validates the response status and body against the spec.
4. It writes one structured log line with the `operationId`, the result, and the schema path of each mismatch.

Some rules for this middleware:

- It never blocks or changes a request.
- It does not log body values, because the bodies can contain customer data. It logs only the schema paths that fail.
- It runs with strict checks, so it treats `additionalProperties` as false. Then it reports fields that the API returns but the spec does not document.
- You can turn on sampling if the check is too slow.

Turn it on in local dev, staging, and internal dogfood instances. The frontend calls most of these APIs, so normal use covers many routes.

Does middlewares in express have access to both request and response?

--- ASSISTANT  2026-09-30 09:54 UTC ------------------------------

Yes, but with one limit. An Express middleware gets the `req` object and the `res` object. It can read the full request. It cannot directly read the response body.

## Why the response body needs extra work

The middleware runs before the route handler. At that time, the response does not exist yet. Later, the handler writes the body with `res.json()`, `res.send()`, or `res.write()`. Express sends that body and does not keep a copy.

## How to get the response

| Method | What you get |
|---|---|
| `res.on('finish', ...)` | Status code and headers only, after Express sends the response |
| Replace `res.json` before you call `next()` | The body object, before Express converts it to JSON |
| Replace `res.write` and `res.end` | The raw bytes of each chunk |

Here is an example of the second method:

```ts
app.use((req, res, next) => {
  const originalJson = res.json.bind(res);
  res.json = (body) => {
    checkResponse(req, res.statusCode, body); // log only, never throw
    return originalJson(body);
  };
  next();
});
```

`express-openapi-validator` uses the same method for its response validation.

## What this means for this codebase

- About 420 places in `modules/` and `libs/` send the response with `.json(`. The `res.json` replacement covers all of them.
- 3 places use `res.send(`. You can replace `res.send` in the same way.
- Some routes stream the response with `res.write(` (38 uses) or `.pipe(res` (2 uses). Most of these are Server-Sent Events (`text/event-stream`) in `es_controller.ts`, `kb_controllers.ts`, `cm_controller.ts`, and `enterprise_search/utils/utils.ts`. For these routes, the middleware should check only the status code and the `Content-Type` header. A body check for a stream is difficult, and OpenAPI cannot describe event streams well.

Thus, the plan works for most routes. The streaming routes need a smaller check, or they go into the `unobserved` status.

## Limits to plan for

1. **Valid IDs.** Many paths need real IDs, for example `{kbId}` or `{recordId}`. Random IDs give only 404 responses, so the run checks only the 404 schema. You need seed data, and the tool must get IDs from earlier responses. OpenAPI `links`, or a small config file that maps each parameter to a source, can do this.

You are right. Response validation cannot find this type of error. The fix is to test the boundaries: send values at and just outside each documented limit, then compare the backend result with the spec.

## Why response validation misses it

Response validation checks what the API returns. The limits on `limit` control which requests the API accepts. To test them, you must send values near each limit and look at the status code.

## Two checks for each constrained parameter

Change one parameter at a time. Keep all other inputs valid.

| Check | Send | Expected result | If it fails |
|---|---|---|---|
| Positive | A value that the spec allows | 2xx | The spec allows a value that the backend rejects |
| Negative | A value that the spec does not allow | Documented 4xx | The spec rejects a value that the backend accepts |

Your example: the spec says `1 ≤ limit ≤ 50`, but the backend accepts `5 ≤ limit ≤ 100`.

- Send `limit=1`. The spec allows it, but the backend returns 400. The positive check fails, so the documented minimum is wrong.
- Send `limit=51`. The spec rejects it, but the backend returns 200. The negative check fails, so the documented maximum is wrong.

Schemathesis has both checks: `positive_data_acceptance` and `negative_data_rejection`. It also has a negative data generation mode. Verify the exact names against the version you install.

## Find the real limit

The two checks tell you that a limit is wrong. They do not tell you the correct value. For integer parameters, add a boundary probe. It uses a binary search to find the value where the backend changes from accept to reject. For your example, it reports "real minimum is 5, real maximum is 100." The engineer can then update the spec. This takes about 10 to 20 requests for each limit.

## Current state of the spec

I counted the constraints on parameters in `pipeshub-openapi.yaml`. This count does not include request body fields.

- 80 numeric parameters: 41 have both `minimum` and `maximum`, and 39 have only one of the two.
- 405 string parameters: 40 have an `enum`, and 32 have a length limit.

For the 39 parameters with one limit, the boundary probe can find the missing limit too.

## Problems that can hide the result

1. **Clamping.** Many backends accept `limit=500` and return only 100 items. The status is 200, so the negative check reports "accepted." But the backend did not use the value. To find this, the seed data must have more items than the maximum. Then the check compares the number of returned items with the requested value. If the backend clamps, document that in the spec.
2. **Other errors first.** If the ID in the path does not exist, the backend can return 404 before it validates `limit`. Every probe must use valid IDs from the seed data.
3. **Silent defaults.** The backend can replace a bad value, such as `limit=abc`, with a default value and return 200. The clamping check finds this in the same way.
4. **500 errors.** A 500 response to an out-of-range value is a backend bug, not a correct rejection. Report it as a separate result.
5. **Rules between parameters.** OpenAPI cannot describe rules such as "`from` must be before `to`." The probe cannot test these rules. List them in the operation description.
6. **Strings.** Length limits and `enum` values are easy to test. For an `enum`, send each documented value and one value that is not in the list. `pattern` limits are difficult to probe, so test them only with examples.

## Where this goes in the report

Add one column for each operation, such as `constraints: ok / drift / untested`, and add a list of each wrong limit with its real value. This check uses the same generated run, OAuth client, seed data, and temporary instance as the response check. It adds a different request strategy, but no new infrastructure.

## What the ITs do today

Some ITs test input limits, but only for a few endpoints, and they hard-code the values. For example:

- `integration_test_agent_conversation_listing.py` expects `limit=0` and `limit=101` to fail.

These tests compare the backend with numbers that a person typed into the test. They never read the spec. So if the spec says "maximum 100" and the backend accepts 200, the IT still passes, and nobody sees the error in the spec.

## A real example in the code today

For `GET /agents/{agentKey}/conversations/show/archives`, the spec says that `limit` has `maximum: 100`. So `limit=101` is invalid. But the IT at `integration_test_agent_conversation_listing.py:978` expects the backend to accept `limit=101` with status 200, and then quietly reset it to 20. The IT also expects `page=0` to become 1. The spec does not describe this reset. So the spec and the backend do not agree, and the IT passes without showing it.

The contract job finds this case:
- `negative_data_rejection` sends `limit=101`, gets 200, and reports that the backend accepts a value that the spec forbids.
- The clamping check sees 20 items where 101 were requested, and reports "reset to default."

## What the contract job covers for inputs

| Type of input check | Contract job | ITs today |
|---|---|---|
| Documented minimum and maximum (80 numeric parameters) | All, automatically | A few, hard-coded |
| Real limit values when the spec is wrong | Yes (`probe_bounds.py`) | No |
| Quiet reset or clamping | Yes (clamping check) | Only where someone wrote an assertion |
| Enum values (40 parameters) | All documented values plus one invalid value | A few |
| String length (32 parameters) | min−1, min, max, max+1 | Rarely |
| Required fields missing | Yes (negative mode) | Some |

## What the contract job cannot check for inputs

It can only test the rules that the spec contains. So these cases stay with the ITs:

- **Rules that are not in the spec.** For example, the ITs expect a blank `search` value (`"   "`) to fail. If the spec has no `minLength` or `pattern` for it, Schemathesis does not know that the value is invalid.
- **Rules between parameters.** For example, `startDate` must be before `endDate`. OpenAPI cannot describe this rule.
- **The content of the error.** The ITs check that the error body has details (`error.metadata.errors`). Schemathesis checks only the status code and the schema.
- **Parameters with no limit in the spec.** The probe can find a missing maximum for the 39 parameters with only one limit. But if the spec has no limit and no type, the job cannot test it.

- Do not write new range ITs by hand. The contract job tests every documented limit.
